# M5.5 — UI-Support Endpoints (registry, upload, result download)

> **Superseded in part by M6:** the in-memory `BUILT_MACROS` registry
> described below was replaced with a real SQLite database (`db.py`)
> during M6 — see [M6-frontend.md](M6-frontend.md). `GET /macros` no
> longer goes empty on a restart. Everything else on this page (the
> upload/result-download endpoints, the `MINIO_ENDPOINT` split) is still
> accurate as of M6.

## What was built

Three endpoints on `services/backend-api/main.py`, closing the gap between
what the API could already do and what a UI needs — the API could build
and run a macro, but there was no way to *list* what had been built, no
way to get an input file in without the `mc` CLI, and no way to get a
result out without it either.

- **`GET /macros`** — lists every macro built so far, from a new in-memory
  registry (`BUILT_MACROS: dict[str, dict[str, str]]`). `POST
  /macros/{macro_name}/build` now records `{macro_name: {"image_tag":
  ..., "built_at": <ISO timestamp>}}` on success.
- **`POST /macros/{macro_name}/input`** — accepts a file upload
  (`UploadFile`, multipart/form-data) and writes it directly into MinIO at
  `radio-data/{macro_name}/input.csv` via a new `build_minio_client()` in
  `main.py`, overwriting whatever was there. Returns a confirmation
  (`macro_name`, `object_key`), not the file contents.
- **`GET /executions/{job_name}/result`** — looks up `macro_name` from a
  second new in-memory map, `JOB_TO_MACRO: dict[str, str]` (populated by
  `POST /executions/{macro_name}` on success), then streams
  `macro-results/{macro_name}/output.csv` back as `text/csv`
  (`StreamingResponse`). 404 if `job_name` was never recorded (unknown or
  mistyped); 409 if the macro is known but the output object doesn't
  exist in MinIO yet (execution still running, or failed before
  uploading — see `templates/wrapper.py`'s upload-only-on-success
  behavior from M3).

All three require the existing JWT auth (`dependencies=[Depends(get_current_user)]`),
same as every endpoint since M4.

This is also the first time `backend-api` itself talks to MinIO's API
directly, rather than only setting env vars for a Job's `wrapper.py` to
use. `build_minio_client()` in `main.py` mirrors `templates/wrapper.py`'s
function of the same name (same client construction, same `secure=False`
reasoning) but is a separate copy, not a shared import — `wrapper.py` is
copied verbatim into every generated macro image and isn't meant to be
imported as a library.

**Bug found and fixed along the way:** `MINIO_ENDPOINT` was a single
hardcoded `"minio:9000"` constant, used both for Job env vars
(`build_job_manifest`) and — once `build_minio_client()` needed it too —
for `backend-api`'s own connection. Jobs run *inside* the cluster, where
`minio:9000` resolves via Kubernetes DNS; `backend-api` runs on the host
(outside the cluster), where it doesn't. Split into two constants:
`JOB_MINIO_ENDPOINT` (always `"minio:9000"`, only used in
`build_job_manifest`) and `MINIO_ENDPOINT` (env-var overridable, default
`JOB_MINIO_ENDPOINT`, used by `build_minio_client()`) — same pattern
`vault_client.py`'s `VAULT_ADDR` already used for the identical
host-vs-cluster problem. Overriding the host process's own endpoint
(`MINIO_ENDPOINT=localhost:9000` with a `kubectl port-forward svc/minio
9000:9000` running) no longer risks leaking into a newly created Job's
env vars.

Verified end to end against `rtwp-anomaly-demo`, entirely through the API
(backend-api run on the host with `VAULT_ADDR`, `VAULT_TOKEN`, and the new
`MINIO_ENDPOINT` pointed at `kubectl port-forward`ed Vault/MinIO Services):

1. `GET /macros` — empty on a fresh process (the registry is in-memory,
   see below), then rebuilt `rtwp-anomaly-demo` and confirmed it appeared
   with the correct `image_tag`/`built_at`.
2. `POST /macros/rtwp-anomaly-demo/input` with `sample_input.csv` — `200`,
   then `mc cat local/radio-data/rtwp-anomaly-demo/input.csv` confirmed
   the MinIO object is byte-for-byte identical to the uploaded file.
3. `POST /executions/rtwp-anomaly-demo` → polled `GET
   /executions/{job_name}` to `succeeded`, as in every prior milestone.
4. `GET /executions/{job_name}/result` — `200`, `content-type: text/csv`,
   body byte-for-byte identical to both the raw MinIO object (`mc cat
   local/macro-results/rtwp-anomaly-demo/output.csv`) and a prior stored
   correct run's output. Also confirmed `404` for an unrecognized
   `job_name`.

9 new tests added (`test_main.py`, `test_main_auth.py`): auth-gating for
all three new endpoints, `GET /macros` empty-then-populated, upload
writing to MinIO with the right bucket/key, and all three result-download
outcomes (404 unknown job, 409 no output yet, 200 with correct content and
content-type). Full suite: 76 passed.

## Why it was built this way

- **An in-memory dict, not a real database.** This is a deliberate
  simplification, not an oversight — it's basically a tiny stand-in for
  the audit log the original PFE report kept in SQLite. Enough to answer
  "what's been built" and "which macro did this job run" for a demo; not
  meant to survive a restart or be queried for anything beyond that. A
  real datastore is worth adding once either of those stops being true —
  not speculatively now, per this project's own "don't build toward later
  milestones prematurely" rule.
- **Two endpoint constants (`JOB_MINIO_ENDPOINT` / `MINIO_ENDPOINT`), not
  one collapsed into an env-var override.** The alternative — overriding
  the single old `MINIO_ENDPOINT` constant when running `backend-api` on
  the host — would silently break every Job created while that override
  was set, since `build_job_manifest` read the same constant. Keeping
  them separate means the override only ever affects `backend-api`'s own
  connection.
- **`backend-api`'s own `build_minio_client()`, not an import from
  `templates/wrapper.py`.** `wrapper.py` is a static template copied
  verbatim into every generated macro image (see M3) — it's meant to be
  identical and self-contained inside that image, not a shared dependency
  `backend-api` also imports. Duplicating the ~10-line client constructor
  is simpler than restructuring either side around a shared import for
  this little code.
- **404 vs. 409 in `GET /executions/{job_name}/result`, not one error
  code for both.** An unrecognized `job_name` (404) and a real job whose
  result just isn't ready yet (409) are different situations a caller
  needs to tell apart — the first means "check the name," the second
  means "poll again later." Collapsing them into one status would lose
  that distinction for no benefit.
- **`length=len(contents)` on `put_object`, reading the whole upload into
  memory first.** MinIO's `put_object` needs a known length up front (or
  a more complex multi-part-upload path for unknown-length streams).
  Macro input files are small CSVs, not large uploads, so reading fully
  into memory first is the simple, correct choice here — not something
  that needs streaming yet.

## What was deliberately left out

- No pagination, filtering, or sorting on `GET /macros` — it returns
  everything in the registry, in insertion order. Fine at the scale of "a
  few demo macros," not designed for more.
- No validation of the uploaded file's content or schema in `POST
  /macros/{macro_name}/input` — any bytes are accepted and written as
  `input.csv`. The macro itself (or, eventually, `rules.yaml`-based
  validation, still not built as of M3) is what will fail on a bad
  input, same as every milestone so far.
- No cleanup of `JOB_TO_MACRO` or `BUILT_MACROS` entries — they grow for
  the lifetime of the process. Not a real leak at demo scale, but not
  something meant to run unattended for a long time either.
- No way to delete or overwrite a macro's registry entry short of
  rebuilding it, and no way to re-fetch a result after the responsible
  process has restarted (the map is gone). Both are consequences of the
  in-memory-registry simplification above, not separate gaps.
