# M6.5 — Monaco Code Editor

## What was built

Replaced the plain `<textarea>` used for macro source code (in both the
create-macro and edit-macro forms — they share one component,
`MacroForm.jsx`) with a real code editor: Monaco, via
`@monaco-editor/react`.

- **`services/frontend/src/components/CodeEditor.jsx`** (new) — a thin
  wrapper around Monaco's `<Editor>`. Same `value`/`onChange` contract the
  textarea already had, so `MacroForm.jsx`'s `sourceCode` state and
  `handleSubmit` needed zero changes — this is a presentation-layer swap,
  not a data-flow change. A custom theme (`signal-dark`), not Monaco's
  stock `vs-dark` left as-is: colors are pulled directly from
  `index.css`'s existing tokens (`signal-800` background, amber
  keywords/cursor, `signal-400` comments) so the editor reads as part of
  this app's palette, not an unrelated dark theme dropped in next to it.
- **`services/frontend/src/monacoSetup.js`** (new) — configures Monaco to
  run entirely from the locally-installed `monaco-editor` package instead
  of `@monaco-editor/react`'s default behavior of fetching Monaco from
  jsdelivr's CDN at runtime. Imported once in `main.jsx`, before anything
  renders.
- **`services/frontend/src/pages/MacroForm.jsx`** — the `<textarea>` is
  gone; its label changed from `<label htmlFor="macro-source">` to a
  plain `<span>`, since Monaco renders its own internal textarea with a
  generated id, so the old `htmlFor` no longer pointed at anything real.
- **`package.json`** — added `@monaco-editor/react` and `monaco-editor`
  as direct dependencies.

## Why it was built this way

- **Bundled locally, not loaded from a CDN.** This project has otherwise
  never depended on reaching the internet at runtime — k3d, MinIO, and
  Vault all run locally, and Vault dev mode's own secrets have to be
  re-seeded by hand on every fresh pod (see
  [003-vault-secret-management-simplifications.md](003-vault-secret-management-simplifications.md)).
  Leaving Monaco on the CDN default would have made the create/edit macro
  form silently fail to render an editor the moment there's no internet
  connection — a new, unannounced exception to how this app has worked so
  far. Flagged explicitly and confirmed before implementing, not decided
  silently.
- **`editor.api` core plus a manual Python-only language registration,
  not the package's root `monaco-editor` entry point.** The root entry
  eagerly registers Monarch tokenizers for every language Monaco ships —
  SQL, Ruby, Solidity, TypeScript's full language service, dozens more —
  none of which this app ever needs; a first pass at bundling Monaco
  this way produced a single 4.3MB JS chunk full of languages nobody
  asked for. Importing `editor/editor.api` (Monaco's own documented
  "core editor only" entry point) and registering just Python's Monarch
  tokenizer + language configuration
  (`languages/definitions/python/python.js`) brought that down
  significantly and reduced the build from ~30 per-language chunks to
  two: the app bundle and a separate editor Web Worker chunk.
- **`node_modules`-relative imports in `monacoSetup.js`, not bare package
  subpath specifiers.** `monaco-editor`'s own `package.json` `exports`
  map only declares its root entry point (`"."`), not the deep subpaths
  (`esm/vs/editor/editor.api.js`, `esm/vs/languages/definitions/python/python.js`,
  the worker file) that Monaco's own documentation tells you to import.
  This project's Vite 8 (Rolldown-based) enforces strict ESM
  `exports`-map resolution, so a bare specifier for any of those subpaths
  fails to resolve at build time even though the files exist on disk.
  Reaching into `node_modules` via a relative path from `monacoSetup.js`
  sidesteps package-export resolution entirely. This is the one part of
  the setup tied to this project's exact `node_modules` layout rather
  than a portable pattern — worth revisiting if a future `monaco-editor`
  release adds proper subpath exports, or if the project ever needs a
  cleaner abstraction (e.g. a dedicated Vite plugin) over this.
- **Worker registered via `new URL(..., import.meta.url)` + native
  `Worker`, not the `?worker` import-suffix syntax Monaco's docs usually
  show.** The `?worker` suffix (a Vite-specific convention) failed to
  resolve against this same package-subpath issue under Vite 8/Rolldown.
  The URL-constructor form is plain ES module syntax every modern bundler
  already understands as "give me this file's built URL," so it isn't
  tied to a bundler-specific plugin feature that can regress between
  major Vite versions the way `?worker` just did.
- **Only `editor.worker` registered, no language-service worker.** Monaco
  core ships a Monarch tokenizer for Python — enough for the syntax
  highlighting this component needs — but no dedicated Python *language
  service* worker the way it does for TypeScript/JSON/CSS/HTML (no
  autocomplete/diagnostics engine). There's nothing to point a second
  worker at, so none is registered.

## What was deliberately left out

- No Python language server / autocomplete / inline diagnostics — Monaco
  core only ships syntax highlighting for Python (a Monarch tokenizer),
  not a language service. Real-time linting or autocomplete would need a
  separate language server (e.g. Pyright via a Language Server Protocol
  bridge) — out of scope for a visual editor upgrade.
- No editor settings/preferences (font size, keybinding profile, etc.) —
  a single fixed configuration (13px JetBrains Mono, line numbers on, no
  minimap) matches the rest of the app's fixed, non-configurable design
  system.

## Verification

Confirmed the editor swap has zero effect on the existing structured
error-handling pass (`ast_engine.py`'s `MacroSyntaxError`,
`api/client.js`'s `MacroSyntaxError`/`BuildFailedError`, `MacroForm.jsx`'s
`BuildError` component) — Monaco only ever produces a plain string that
flows into the same `buildMacro()` call the textarea did:

1. Submitted a dangling `if x:` directly against the running API → `422`,
   `{"error":"syntax_error","message":"expected an indented block after
   'if' statement on line 3","line":3,"source_line":"if x:"}` — the exact
   shape `BuildError`'s syntax-error panel renders, unchanged.
2. Rebuilt `rtwp-anomaly-demo` with its own unchanged valid source → `200`,
   full success response (`image_tag`, `imports`, `required_columns`,
   `artifacts`), completely unaffected by the editor swap.
3. Catalog still showed exactly 5 macros afterward — the throwaway syntax-
   error test never reached `db.upsert_macro`, no phantom registry entry.

`pytest services/backend-api/` — 145 passed (this was a frontend-only
change; run anyway per the project's standard verification discipline).
`npm run build` / `npm run lint` (oxlint) both clean.
