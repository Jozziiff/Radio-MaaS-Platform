# M6.75 — OpenCelliD Tower Data

## What this is about

The web app is about to gain a feature that needs real-looking geographic
context for Orange Tunisie's network around Tunis. Rather than inventing
fictional tower coordinates, this fetches real, public, crowdsourced cell
tower data from [OpenCelliD](https://opencellid.org) and caches it as a
static JSON file the frontend reads directly -- no live per-request API
call, no OpenCelliD dependency in the running app at all.

## What was built

- **`services/backend-api/scripts/fetch_towers.py`** (new) — a standalone
  script, not part of the running FastAPI app and not imported by
  `main.py`. Queries OpenCelliD's `GET /cell/getInArea` endpoint (the
  exact endpoint and parameter names were verified directly against
  <https://wiki.opencellid.org/wiki/API> before writing any code, not
  assumed from prior knowledge or older documentation) for a bounding box
  covering greater Tunis (`36.65,10.05` to `36.95,10.35`), filtered to
  `mcc=605` (Tunisia) and `mnc=1` (Orange Tunisie specifically --
  Tunisie Telecom is `mnc=2`, Ooredoo is `mnc=3`). Writes the result to
  `services/frontend/src/data/orange_towers.json`: a flat array of
  `{cell_id, lat, lon, range_m, radio, samples}`, dropping every other
  field the API returns (`mcc`/`mnc`/`lac`/`averageSignalStrength`/
  `changeable`/radio-specific extras like `rnc`/`cid`/`tac`) since the
  frontend's map only needs enough to place and describe a marker.
- **Tiling, discovered necessary only by actually hitting the real API.**
  The wiki page's own documentation doesn't mention a per-query area cap,
  but the live API rejects any single `BBOX` over ~4,000,000 sq meters
  (`{"error": "BBOX too big - Limit to 4,000,000 sq.mts.", "code": 3}`).
  The full Tunis bounding box is roughly 33km x 27km — far over that — so
  the script splits it into a grid of 0.018°-square tiles (~289 tiles for
  this box) and queries each one separately, paginating within a tile via
  the API's own `limit`/`offset` when a tile has more than 50 cells (the
  API's own documented per-request maximum). Results are deduplicated by
  `cellid` across tiles.
- **Resumable, not all-or-nothing.** A sidecar progress file
  (`scripts/.fetch_towers_progress.json`, gitignored) records which tile
  indices have already succeeded and every cell collected so far,
  updated after *every* tile, not just at the end. If a run is
  interrupted (a quota error, a network drop), re-running the script
  picks up exactly where it left off instead of re-querying tiles that
  already succeeded — important because a successful query still counts
  against the API's daily quota even if the *script* is re-run from
  scratch. `orange_towers.json` itself is only ever written on a fully
  complete run — a partial run leaves the last known-good complete file
  (if any) untouched rather than overwriting it with an incomplete one,
  and exits non-zero with a clear message pointing at the progress file.
- **Loud failure on zero results, not a silent fallback.** If a
  *complete* run finds zero towers for `mcc=605`/`mnc=1` in the bbox,
  the script refuses to write an empty or unfiltered-fallback file and
  exits non-zero with an explicit message to check the bbox/mnc filter
  instead. (A partial run finding zero towers *so far* is not treated as
  this case — it just hasn't reached a populated tile yet.)

## Why it was built this way

- **A one-time script, not a live per-request API call.** OpenCelliD's
  own daily request quota (see below) makes it unsuitable as something
  the running app calls on every page load or every request — the data
  changes slowly (real towers don't move often), so fetching it once and
  caching the result as a static asset is the right shape, not a
  simplification made for convenience.
- **Verified the real API before writing any code.** The task explicitly
  required fetching the live wiki page first rather than trusting
  training data or older documentation, and that turned out to matter
  twice over: the wiki's own text states a 1000-requests/day limit, but
  the live API's actual error message says **5000** — a real,
  first-hand-confirmed discrepancy between the documentation and the
  deployed service, not a typo in this script. The area-size cap
  (`code: 3`) isn't mentioned in the wiki excerpt fetched at all; it was
  only discovered by deliberately triggering it against the real API.
- **`mnc=1`, not `mnc=01`.** The task described the filter as "net/mnc=01"
  as shorthand for "Orange's MNC code," but the live API's own example
  usage shows the parameter as a plain, non-zero-padded integer
  (`mnc=2` in the wiki's own example). Sending a zero-padded string
  would likely just fail to match rather than error loudly, so this was
  confirmed against a real example before writing the query, not
  guessed.
- **Deduplication by `cellid`, not by coordinate.** OpenCelliD documents
  `cellid` as a unique identifier per cell; a coordinate-based dedup
  would risk collapsing two genuinely distinct cells that happen to
  report very close (but not identical) coordinates.
- **Per-tile progress checkpointing, not a single all-or-nothing
  request.** Discovered necessary in practice, not designed
  speculatively in advance: the first real run against the full Tunis
  bbox was cut short by the daily quota partway through (213 of 289
  tiles completed) with real data already collected for the completed
  tiles. Without resumability, that entire run's real API usage would
  have been wasted the moment the quota reset and the script had to
  start over from tile 1.

## Data license and attribution

OpenCelliD's database is licensed **CC BY-SA 4.0**. This is real,
public, crowdsourced data — submitted by contributors' phones over time,
not Orange's own proprietary infrastructure records — and its coverage
and accuracy are **not guaranteed**: gaps are expected in areas with
fewer contributors, and some entries may be stale, duplicated, or
imprecise (a specific example seen while testing: several nearby cells in
one small test area all reported `range_m: 1000` and `samples: 1`,
consistent with default/placeholder values from a single low-confidence
submission rather than a verified reading — this app does not attempt to
filter or "clean" that, since doing so without real ground truth would
just be guessing).

**"Data: OpenCelliD" (or equivalent visible credit) must appear wherever
this data is displayed in the app**, per the license's attribution
requirement. This is a hard requirement, not a nice-to-have — noted here
so the UI work that consumes `orange_towers.json` doesn't ship without it.

## What was deliberately left out

- **No automatic/scheduled re-fetch.** This is a manual, run-by-hand
  script (`OPENCELLID_API_KEY=... python scripts/fetch_towers.py`), not
  a cron job or a step in any CI/deploy pipeline. Real towers don't
  change fast enough to justify that complexity yet.
- **No retry/backoff on a single failed HTTP request within a tile** —
  a network blip mid-tile fails that tile's fetch and the whole run
  (falling back to the resumability described above), rather than
  silently retrying and risking masking a real problem.
- **`OPENCELLID_API_KEY` is a plain environment variable, not
  Vault-sourced** — this script doesn't run as part of the deployed
  application at all, so it sits outside the Vault-backed secrets model
  `vault_client.py` provides for `backend-api` itself (JWT signing key,
  MinIO credentials) and `GITEA_TOKEN`'s already-flagged gap. Consistent
  with both of those: the key must never be hardcoded or committed, and
  is only ever passed via the environment at invocation time.

## Status as of this write-up

Two more runs (a resumed run, then one cut short again) confirmed
resumability works exactly as designed: a mid-run network reset at tile
43 was recovered from with zero data loss, and the run eventually hit
the real daily 5000-request quota again at tile 238/289 — but this time
with 6,669 towers already checkpointed and safely preserved rather than
discarded.

**`services/frontend/src/data/orange_towers.json` now exists**, written
via a new `--export-partial` flag on `fetch_towers.py` that writes out
the current checkpoint's already-deduplicated cells as-is, without
touching the network or requiring an API key. This is a **partial fetch
— 237 of 289 tiles (6,669 towers)**, not the full bounding box; the
remaining ~52 tiles (mostly toward the edges of the box, since the tile
grid is filled in row-major order) haven't been queried yet.
`--export-partial` deliberately leaves `.fetch_towers_progress.json` in
place rather than deleting it the way a complete run does, so a later
top-up run can resume from tile 238 and simply overwrite
`orange_towers.json` with the fuller result — no reprocessing of the
6,669 already-collected towers, no wasted quota re-fetching tiles
already done. Sanity-checked before shipping: every coordinate falls
inside the Tunis bounding box, density is highest in central Tunis as
expected, and a spot-check central sub-box (~4km²) alone contains 842
towers — comfortably above what a demo map needs, so the partial file is
usable as real data now rather than something to wait on.
